# D210 CPU の MCTS 拡張仕様・実装方針

## 位置付け

現在の通常対局 CPU（`src/ai/MatchCpuDefaults.js` の D210）を維持し、その先に起こり得る配置・得点を読む層としてモンテカルロ木探索（MCTS）を追加する。最初の対象は **スタンダード・2人戦・手札1枚**。ルール、合法配置、得点、山札構成は既存のゲーム仕様と `GameEngine` を正とし、MCTS 専用の緩和を通常対局へ持ち込まない。

既存の「判断記録 JSON → 特徴量 JSON → 重み学習」および教師あり学習は、今後の CPU 強化の主経路にしない。既存画面・スクリプト・保存済み JSON はこの仕様策定段階では変更・削除しない。新しい特徴量 JSON、ニューラルネットワーク、AlphaZero は対象外。D210 の重みを再学習することも初版の目的ではない。MCTS が実測で有効と確認できるまでは、通常対局の既定 CPU は D210 のままとする。

### 現行コードとの重要な相違

- `chooseCpuAction` は盤面全体の `evaluate(state, weights)` ではない。合法な **タイル配置とミープル選択の組**を相対評価する関数である。添付案のように葉局面をそのまま D210 で評価することはできない。D210 は候補の順序付けと探索中の方策に再利用し、葉には別途、得点差を返す小さな局面価値アダプターを設ける。
- `GameEngine` に探索用の盤面複製・巻き戻し API はない。`Board` や配置・確定配置のキャッシュを含むため、オブジェクトを単純に `structuredClone` しても同じエンジンとして動かない。まずルールを共有する探索用状態の複製と遷移を設計・検証する。
- Node の自己対戦とブラウザ CPU 呼び出しは既にある。新しい `game-engine.js` 等へ書き直すのではなく、`src/game/` と `src/ai/` の既存構成へ追加する。
- 通常盤面では合法候補と確定配置の探索が重い。添付案の「まず全合法手で 5,000 simulation、枝の制御は後から」は性能面で前提にできない。実測を先行し、候補の段階的展開と計算予算の制御を初版から入れる。

## 探索する手とゲームの遷移

1手は `タイルID・位置・形状/向き・辺記号パターン・地形パターン・ミープル配置先または置かない` の組とする。実際に同じゲーム状態へ至る重複手だけを統合する。画像やタイル種が同じでも、接続、所有者、後続の合法手が違えば統合しない。

根では既にゲーム側が求めた合法候補を再利用する。手の適用は探索専用の状態に対し、実対局と同じ `placeTile` → `placeMeeple` / `skipMeeple` → 完成得点・ミープル回収・称号処理 → 次の手番という順序で進める。合法候補がないタイルの自動破棄、終局処理も既存挙動に合わせる。任意の引き直し権は初版の探索手に含めず、既存 D210 と同じ扱いにする。盤面・山札・プレイヤーを実対局のオブジェクト上で書き換えない。

タイル配置とミープル選択を独立した木の2手番にはしない。同じプレイヤーの意思決定なので、一組を1行動として扱う。ただし枝数を抑えるため、配置候補を順位付けしてから、その配置で合法なミープル選択を展開できる構造にする。

### 探索用状態を用意する順序

まず `GameEngine` に、進行中の局面から探索専用インスタンスを作る明示的な `forkForSearch` 相当の入口を設ける。通常のコンストラクターは山札をシャッフルして初期タイルを配置するので、局面複製には流用しない。`Board` は新しいインスタンスを作ってタイルを追加し直し、辺・頂点インデックスを再構築する。プレイヤー、得点、ミープル、得点済み領域、称号進捗、手番、ルール、現在のタイルなどの**可変状態**は独立に複製する。タイル定義のような不変データだけ共有する。候補・確定配置・地形完成可能性のキャッシュは、複製後も意味が同じと証明できるもの以外は共有しない。

山札の実順序は複製しない。探索用の「次のタイルを抽出して渡す」入口を分離し、公開残枚数から抽出したタイルを既存の `nextTurn` 相当の処理へ渡す。初版は正確さ優先で複製・再構築を行い、遅ければ1回の simulation 内で適用/巻き戻しできる差分記録や、安全な増分キャッシュへ置き換える。単純な `structuredClone(engine)` や、元の `state.deck` を複製して未来の順番を読む方式は使わない。探索結果と実エンジンの状態遷移を同じ局面で照合する回帰テストを先に作る。

## 情報と確率ノード

CPU が知るのは公開盤面、公開得点・ミープル、見えている手札・破棄札、および定義済み山札から計算した残りの**種類別枚数**だけ。実エンジンが内部に持つ `state.deck` の順番は検索木へ渡さない。現在の `createCpuObservation` と `publicRemainingTilePool` の境界を維持する。通常の1枚手札では次タイルは未知であり、決定手の後に確率ノードを置く。

確率ノードでは残存枚数に比例して種類を非復元抽出する。抽出後はその種類の残数を1減らす。全種類の子を毎回列挙せず、訪問された結果だけを作る。確率ノードを UCT で有利なタイルへ恣意的に誘導してはならない。山札切れ、置けないタイルの破棄、ゲーム終了も抽出後の実ルールに従う。探索用乱数は山札生成用乱数や D210 の同点処理と分離し、シードで再現できるようにする。

将来、公開手札3枚や3〜4人戦へ拡張する際は、公開手札・手番・パスを状態に含め、価値の視点を再定義する。初版の2人・1枚手札用の木をそのまま適用しない。

## MCTS の計算

- **選択**：手番ノードでは UCT を使用する。各ノードの価値はそのノードで行動するプレイヤーの視点に揃え、相手手番で符号を誤って根プレイヤーに有利な相手手を選ばないようにする。確率ノードは前節の確率抽出を行う。
- **展開**：合法候補の軽量な順位と D210 評価を利用する。ただし D210 の全候補詳細評価や既存の戦術先読みを、各 simulation の各ノードで無制限に再実行しない。同一探索状態の候補・順位・価値は探索中に再利用する。根では全合法手を選択可能な集合として保持し、下位候補も訪問数に応じて段階的に展開する。上位だけへ恒久的に切り捨てず、位置・地形・ミープル選択の多様性も確保する。
- **D210 に依存しない探索枠**：妨害・便乗・略奪の準備手は、配置した瞬間の D210 評価が低くても残す。根では D210 上位枠と別に、低順位からのシード付き無作為抽出枠、異なる盤面位置・隣接地形・ミープル選択を拾う多様性枠を確保する。割合は固定の強さとして決め打ちせず、1秒の予算内で展開数を実測して調整する。段階的展開の条件に D210 順位だけを使わない。相手の手についても D210 上位だけを仮定せず、同様に不利な応手・低順位の準備手を探索できるようにする。
- **ロールアウト**：D210 に由来する軽量な手の順位からの抽出と、順位に依存しない抽出を混ぜる。比率を設定・比較できるようにし、D210 方策だけで全ロールアウトを固定しない。相手にも同じ合法判定を適用する。重い D210 詳細評価と局所戦術探索は、根やごく少数の展開候補に限定する設定を持つ。`currentAI` を全ロールアウトで毎回呼ぶことは初版の必須条件にしない。木の訪問後の価値は実際の仮想遷移と葉評価から更新し、D210 の初期順位を報酬に加算し続けない。
- **葉**：最大手数・予算到達または終局で評価する。終局は `GameEngine` と同じ最終得点差を使う。非終局では、確定済み得点差に、既存 `Scoring` を利用した未完成地形・草原・称号の終局見込みを加えた**新しい局面価値アダプター**を定義する。所有者への配点は同数最多を含め実ルールに従い、完成済み得点を二重計上しない。D210 の行動価値を局面得点へそのまま足さない。局面価値の計算費用と妥当性は単独テストで測る。
- **逆伝播**：全訪問数と根視点の価値を更新する。手番ノードで利用する際は行動プレイヤー視点に変換する。価値は得点差の大きさによる暴走を防ぐため、決めた正規化を同じ対局内で一貫して使用する。
- **最終選択**：根の訪問数最大を基本とし、同数なら平均価値・D210 順位・シード付き同点処理の順に決める。探索が完了しない、または有効な simulation が不足した場合は合法な D210 の手へ戻す。

固定の最大手数は暴走防止の上限であり、常にそこまで完全展開する意味ではない。都市・道の完成や所有者逆転などでの戦術的延長は初版の正しさ・速度を確認した後に検討する。「妨害」「便乗」「略奪」を専用の合法ルールにせず、得点差と応手から効果を読ませる。ただし探索できる距離や予算では見えない戦術があることを評価時に明示する。

## 性能と実行形態

### 自己対戦用の固定盤面

初期の自己対戦・探索予算調整には、既存の `training-patterns/standard-training-v1` の約1200枚規模の3パターンと `FixedTrainingLayout` を使う。対戦ごとにスタンダード山札を別シードでシャッフルし、引いた開始タイルと同じ形状の、パターン中央に最も近い位置へ初期タイルを合わせる。以後はパターン内の同形状・同位置・同回転のスロットに限って合法候補を作り、外側への配置を禁止する。地形・辺記号・ミープル・得点の判定は通常どおりとする。これは既存の固定盤面モードと同じ方法で、確定配置の増分探索を省く。MCTS 内の仮想局面でも同じ制限を適用し、通常対局用の動的確定配置探索を誤って呼ばない。

ただし固定盤面では、外側の未確定位置を使う戦術やパターンによる盤面の広がり方を学べない。固定盤面での自己対戦は開発・予算調整の主手段にできるが、通常対局での強さの採用判定は、未使用シード・先後交換に加えて、動的な通常盤面でも少数検証する。

最初に、固定盤面と通常盤面の序盤・中盤・終盤から複数の局面を採り、次の時間とメモリを分けて計測する：探索状態の複製、確定配置、合法候補生成、候補順位付け、1遷移、1ロールアウト、葉評価。特に数百枚以上の確定配置がある通常局面を含める。

添付案の `5,000 simulations / 8 ply` は**既定値にしない**。通常対局の追加思考時間は、**実盤面について事前に行う確定配置・根の合法候補探索を除き、原則1秒以内**を目標とする。MCTS の仮想局面内で発生する探索・候補生成はこの1秒に含める。重要局面では**1手あたり最大5秒**の長考を認める。発動条件（高得点の完成・所有者の変化・勝敗に直結する終盤など）は安価な情報で判定し、通常の1秒枠と長考の5秒枠を明確に分けて記録する。D210 の基準手を先に確保した上で残り時間を MCTS に割り当て、simulation 数と実時間の上限を両方設定する。局面ごとの完了 simulation 数・候補数・思考時間を観察して予算を調整する。1秒以内に意味のある数の完全な simulation が回らない場合、通常手番では D210 をそのまま採用し、MCTS を既定化しない。予算超過時は完成済み結果だけを採用するか D210 に戻す。思考中に画面が固まらないようブラウザでは Worker を検討し、設定変更・対局終了時にキャンセル可能とする。Node とブラウザで MCTS コアと乱数仕様を共有し、UI 演出は探索に混ぜない。

最適化の優先順は、まず探索状態の安価な複製/差分復元と合法候補・確定配置の安全な再利用、次に候補の順序付け・段階的展開、最後に同一局面ハッシュ、木の再利用、並列化である。局面ハッシュには盤面だけでなく、向き・地形/辺記号パターン、ミープル、得点済み領域、称号進捗、手番、見えている手札、残り山札の種類別枚数、ルール設定を含める。正確な同一性を保証できるまで transposition table や木の再利用は有効化しない。

## 実装順と採用基準

1. **計測・状態遷移**：D210 単独の局面別所要時間を基準化する。探索専用の複製・適用 API を作り、実エンジンと同じ配置・得点・終局結果になることを単体テストする。実際の対局状態が探索で変わらないことを確認する。
2. **小規模 MCTS**：2人・1枚手札で、手番ノード、残枚数に従う確率ノード、段階的展開、D210 由来の方策、葉の得点差、逆伝播を実装する。正常に simulation が終わらない場合の D210 フォールバックを入れる。
3. **Node 検証**：固定盤面3パターンを使い、異なる山札シードで先後を交換した組を回す。D210 対 MCTS の勝分負・得点差に加え、1手の平均・上位百分位思考時間、局面別 simulation 数、メモリ、**D210 の初期順位が低かった手の訪問数と採用率**を出す。少数の探索予算を比較する。訓練用固定盤面だけの勝率で採用を決めない。
4. **ブラウザ接続**：操作不能な待ち時間を避け、既存の CPU 手番中断・設定画面・演出と整合させる。通常対局では検証用の選択肢として導入し、速度と勝率の両方が D210 に対して実用的と確認できてから既定化を判断する。

最低限の回帰テストは、合法手のみ返す、同じシードで再現する、山札順を覗かない、残り枚数どおりの抽選、ミープル回収と都市・道・草原・修道院・頂点王の得点一致、相手ノードの価値反転、山札切れと置けないタイル、キャンセル後の対局状態不変を含める。妨害・便乗・略奪については少数の固定局面を作り、D210 単独と MCTS の選択およびその理由となる後続得点差を比較する。

## MCTS 完成後の世代選抜・学習方針

これは探索本体が正しく動き、時間と強さの基準値を測れた後の段階とする。初期の世代学習では **D210 の重みを固定**し、探索定数、枝の段階的展開、D210/非 D210 ロールアウトの比率、探索深さ、長考条件など**少数の MCTS パラメーターだけ**を調整する。探索が安定した後、葉評価の重みを学習対象に追加する。D210 自体の重みは少なくとも初期・次段階では固定し、変更するなら別の実験として評価する。対局時間も適応度の制約とし、通常手番1秒・重要局面5秒の上限を超えて勝率を稼ぐ個体を無条件に採用しない。

### 対戦相手と評価

各個体を一種類の相手にだけ最適化しない。相手プールには、現世代の代表、前世代の代表、合法手から広めに選ぶランダム寄り CPU、高得点の完成・競合・相手地形への介入を優先する攻撃的 CPU を含める。相手の版・設定・乱数シードは記録し、世代中に相手の性格を黙って変更しない。これらは評価用の対戦相手であり、対局ルールや合法判定を変えるものではない。

選抜中は多数の異なる相手・山札シードを使い、先攻をシードでランダム化する。ただし、途中集計で先攻比率や相手の種類が個体ごとに極端に偏らないよう、割り当てを層別化する。相手ごとの勝分負・得点差・対局時間を個別に表示し、弱い相手への大量勝利だけで総合順位を上げない。各相手を同じ重みで集約することを初期案とし、調整する場合は事前に記録する。最終候補は**未使用の山札シードで先後を入れ替えた2局を1組**として、現代表と複数の相手へ対戦させる。最終採用は従来どおり2人戦の勝率を優先し、同率なら得点差を比較する。固定盤面での結果に加えて、通常盤面で少数の確認対局を行う。

### 対局数を抑える段階的選抜

初回から全個体を全相手と同数対戦させない。まず各個体に少数のシード・相手を割り当て、途中結果が良い個体だけ次の対戦枠を与える段階的選抜（successive halving / racing）を使う。各段階では同じシード群と相手構成を可能な範囲で共有し、山札運による分散を減らす。現代表を常に比較対象として残し、強い個体へ対戦枠を集中する。予選の先後はランダム化してよいが、最終評価は先後交換を省略しない。

何度も負けた個体は、相手の強さ・先後・対局数を考慮した不確実性の範囲で、採用候補へ届く見込みが十分低い場合に打ち切る。**単なる連敗数だけでは破棄しない**。対局途中の打ち切りは、終局時の草原・称号や逆転可能性を含む保守的な上限から逆転不可能と判定できる場合に限り、公式の勝敗として扱える。それ以外の大差・低い予測勝率による早期終了は予選用の暫定評価とし、勝敗には数えず「途中打ち切り」と記録する。生き残った個体の最終評価は必ず完走する。これにより、序盤で不利でも終盤に強い個体を系統的に捨てない。

### 敗者からの学習と相関

勝者だけでなく、敗者の全パラメーター差分、相手タイプ、先後、シード、完走/打ち切り、勝敗・得点差・思考時間を保存する。各世代では代表との差分と成績差の関係を推定し、どのパラメーターを増減させたときに結果が変わりやすいかを調べる。勝率だけでなく得点差と時間も別に追う。十分な対局数がない相関は不確実と表示し、偶然の大勝1局を強い因果関係と見なさない。

次世代では有望な方向の変異幅を広げ、影響が小さい方向は狭める。複数パラメーターの相関も後から扱えるよう、低次元の共分散行列を用いる CMA-ES に近い更新を検討する。ただし初期は個体数・試合数が少なく共分散が不安定になりやすいので、変異幅の上下限、共分散の縮小、現代表の保持、未使用シードでの検証を必須とする。途中打ち切りを完走負けと同じ数値で学習器へ入れず、打ち切り情報を別扱いにする。

### さらに優先する高速化

1. **最も有効な節約は対局割り当て**：段階的選抜、相手タイプ別の必要十分な試合数、弱い個体の早期除外により、不要な完走を減らす。全個体総当たりは行わない。
2. **探索予算も段階化**：予選は短い同一予算で粗く比較し、上位のみ通常の1秒予算で再評価する。ただし探索予算を変えると手の選択も変わるため、予選成績と最終成績を混ぜず、予算ごとに記録する。
3. **安全な再利用**：固定盤面の形状スロット索引と不変タイル定義を共有し、同一局面の合法候補や探索済み部分を状態が一致する場合だけ再利用する。盤面が異なる対局間で候補や得点を流用しない。差分状態・適用/巻き戻しは、正確な結果一致を確認してから導入する。
4. **並列化は計測後**：CPUコアが複数ある環境では独立対局を Worker/プロセスへ分ける。ただし全ワーカーが同時に重い盤面複製を行うと逆に遅くなるため、対局/秒とメモリを見て並列数を決める。Worker 起動・JSON 出力・詳細ログの費用を抑え、予選では集計値だけを保持する。

評価効率は「1局の速さ」だけでなく、**所要時間当たりに、未使用シードでも強い個体を発見できた回数**で測る。予選打ち切りや相手プールへの過適合を検出するため、各世代で少数の完走・通常盤面対局を残す。

## 現在の実装と制約

`src/ai/MctsCpu.js` に探索本体、`GameEngine.forkForSearch` に独立した仮想状態、`src/ai/MctsPopulation.js` に個体群のJSON形式と変異・結果集計、`src/ai/MctsTrainingWorker.js` に固定盤面での段階的選抜を実装した。`mcts-training.html` で個体群JSONの読み込み、学習、最新1世代の優秀個体群の書き出しができる。JSONには最優秀個体IDを含め、ゲームの開発用設定で読み込むとその個体を使用する。D210は引き続き既定のCPUで、MCTSの選択は2人・手札1枚の対局だけに対応する。

予選の32手・昇格判定の48手で打ち切った対局は、現時点で対局を終えた場合の得点による**暫定順位**にのみ使う。正式な勝分負としては数えず、最終候補と現代表の先後交換した2局は完走させる。前世代代表は書き出しJSONの `previousChampion` から継承する。敗者の暫定得点差も小さな重みでパラメーター傾向の推定に使うが、表示する相関値は因果関係や統計的な強さの証明ではない。

初版の葉評価は仮想局面をその場で終局させた得点差を使う。これは未完成地形・草原・称号の**現在の終局得点**であり、将来の完成確率を推定するものではない。また、通常盤面の1秒枠では完了できるsimulation数が少ない可能性がある。強さを主張する前に、D210と複数シードで先後交換し、勝率・得点差・思考時間を計測する。通常盤面での長考条件は、現時点では残り山札12枚以下かつ得点差15点以内の終盤とする。必要なら戦術的な重要局面へ拡張する。

### 探索1回の軽量化（実装済み）

`npm run benchmark:mcts -- 12 20` で固定盤面の12手後から20回の探索を区間別に計測できる。末尾に `no-cache normal` を付けると候補キャッシュを無効にした通常盤面で計測する。数値は局面・端末・JITのウォームアップに左右されるため、同条件の繰り返し測定で比較する。

計測では探索用山札の作成・盤面複製・葉の終局採点より、仮想手の後に次のタイルの合法候補を探す処理が支配的だった。そこで、公開残りタイルの雛形は手番の冒頭で一度だけ作り、simulation ごとは並び順だけ抽選する。探索用複製はその後に一度だけ山札を深くコピーする。最大探索深さに達する最後の仮想手では、使わない次手番の候補を生成せず、その盤面を従来と同じ終局採点で評価する。

同一 simulation セッション内では、盤面タイルと現在タイルの完全一致キーで検証済み候補・確定配置フロンティアを最大256局面までキャッシュする。盤面やタイルが変わった過去手番の候補は使い回さない。固定訓練盤面では、保存済みスロットの近くにない盤面の空き辺を候補生成から除き、スロット外の形状候補を高価な重なり・辺記号判定より前に除外する。全辺から探索した従来方式と候補が完全一致する回帰テストを設けた。

固定盤面の初手付近で3 simulation を行った単発計測では平均約0.33秒から約0.13秒、12手後で2 simulation は約0.85秒から約0.48秒になった。12手後の20 simulation では候補キャッシュのヒットが2回で、キャッシュあり約7.06秒、なし約7.35秒だった。通常盤面の初手付近は依然として約0.61秒/simulationで、特に動的な確定配置を伴う次手番候補生成が残る課題である。葉採点と盤面複製はこの測定では小さいため、結果を変える差分採点や巻き戻し型盤面への置き換えは行っていない。

### 学習専用の頂点型拡張テンプレート

学習画面の「学習盤面」では、従来の固定盤面（確定配置探索自体を省略）と、動的盤面のテンプレート高速探索を選択できる。固定盤面が最速の既定値であり、動的盤面を選んだ場合だけ `GameEngine.trainingFastFrontier` を有効にする。MCTS の仮想局面にも同じ設定を引き継ぐ。通常ゲームでも開発用設定から従来探索／テンプレート高速探索を選べる。こちらは非同期の順次描画にも対応する。

高速探索は、sun／moon／king／queen／jack／ace／deuce／star の完成頂点型を最小枚数の仮想タイルで構築し、従来の `structuralPlacementFrontier` で増加が止まるまで探索した結果を、`src/game/TrainingVertexTemplateData.js` に事前保存する。実行時は保存済み座標を読み込んでタイルを組み立てるだけで、頂点型の拡張探索は行わない。辺長120以外は座標を比例変換する。頂点型の規則を変更したときのみ `npm run generate:vertex-templates` で再生成し、生成結果と従来探索の一致テストを通す。元の配置を含む枚数は順に **30／10／99／50／31／7／13／3**。king と queen は当初の概数80枚／25枚より多かった。

学習用探索では、唯一の頂点型を確定できた頂点にテンプレートを回転・平行移動して重ねる。既存の位置は重複追加せず、他タイルと重なるか、頂点型に矛盾する位置があればその頂点は従来方式で探索する。一括追加後の頂点は、周囲のタイル枚数がテンプレートから変わらない間だけ再探索を省略する。後続の実タイル・確定タイルがその頂点へ増えた場合は再び通常どおり調べる。`DGG`／`GGB` のように king と queen の両方があり得る段階は一括追加せず、従来の共通配置判定を使う。

一括配置との照合に使う盤面の占有位置集合は、頂点ごとに全タイルから作り直さず、探索中にタイルが増えたときだけ更新する。これは学習用の同期探索に限定し、通常対局の順次描画経路は変えない。

`npm run benchmark:training-frontier -- 70 19` は同じ乱数シードの動的対局で、毎手番の合法候補と確定位置が一致することを確認し、10手ごとの速度と確定配置枚数を報告する。古い実行時計算方式では seed 19 の40手（確定257枚）でテンプレート生成約2.01秒、手番遷移の合計は従来約9.34秒、高速探索約5.85秒だった。事前保存版では読み込み後の組み立て約2ms、70手の合計は従来約93.9秒、学習用約55.5秒（約1.69倍）。40～50手の区間では確定配置が257枚から787枚に増え、従来約47.8秒、学習用約13.8秒（約3.46倍）。50～70手では新しい確定配置の連鎖が少なく、両方式はほぼ同速だった。両者の合法候補・確定位置は毎手一致した。局面や実行環境で比率は変わる。
