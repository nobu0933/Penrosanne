# CPUの局面特徴量・高速学習仕様

## 目的と適用範囲

手番の判断記録JSON（`penrosanne-decision-record`、版2）から、盤面の位置別情報と全候補手の数値特徴量を**一度だけ**作成し、別のJSONへ書き出す。教師あり学習中はそのJSONを読み、盤面の復元、合法配置、連結地形、先読みを繰り返さない。学習の主対象は当面、2人・スタンダードルール・1枚手札とする。元の対局記録、ゲームの合法判定・得点、通常対戦CPUの重みは、この処理によって変更しない。

既存の `docs/decision-recording.md` の記録形式と `docs/cpu.md` の通常対戦仕様を前提とする。以下の実装済み項目と後続の目標仕様を区別する。

## 実装済みの実行手順

現行のローカル実装では、次の2コマンドで4段階を順に実行する。どちらも新規出力先を指定し、既存ファイルを上書きしない。

```text
npm run precompute-features -- --input battle-detail-data/<判断記録>.json --out battle-detail-data/<特徴量>.json
npm run learn-features -- --features battle-detail-data/<特徴量>.json --out cpu-generation-data/<学習結果>.json --iterations 32 --population 8 --verify-pairs 1
```

第1コマンドは位置別の合法枚数と候補の数値ベクトルをJSONへ保存する。盤面編集から作った記録を拒否し、結果が等価な候補を統合して元候補IDへの対応を残す。第2コマンドは序盤・中盤・終盤の重みを、明示的に評価された代案との比較からCMA-ESで調整する。学習中に盤面・配置規則・得点計算を再実行しない。学習結果は独立のJSONに保存し、`--verify-pairs 1` なら最後に未使用シード・通常盤面で先後交換の2対局を行い、`<学習結果>.json.verification.json` に結果を保存する。自己対戦結果は自動採用に使わない。`--verify-pairs 0` は前処理・学習だけを検査するときの指定であり、正式な検証ではない。

現行の数値化は初版であり、位置ごとの現時点の合法枚数と得点、候補の地形・所有・得点・ミープル消費・頂点・妨害／便乗／略奪の局所指標を含む。位置候補の0件は将来も絶対に埋まらない証明とは扱わない。完成不能の証明は「必要な地形辺を持つ残存タイルが0枚」の場合に限る。将来の相手応手を含む厳密な完成確率、便乗・略奪の2枚ルートとその確率、実対局CPUでの同一特徴量ベクトルの逐次計算は未実装である。学習結果は既存CPUの11重みに変換して自己対戦で検証する暫定方式であり、通常対戦CPUの固定D210へ自動反映しない。

## 処理の流れ

1. 人間の判断記録JSONを読み、形式、ルール設定、選択手、候補ID、山札残数を検証する。通常対局では発生しない盤面を直接編集して作った局面は、学習にも検証にも使用しない。編集局面を含む記録は除外し、除外件数と理由を表示する。判断記録の存在しない手番を、通常の対局局面であると推測しない。
2. 各手番の開始盤面から、完成に関係する位置だけを調べ、残存山札での配置可能性・得点変化などの位置別情報を作る。高価な盤面解析はこの段階に集約する。
3. 記録された**全候補**について、配置後の地形、得点、妨害、便乗・略奪の特徴量を作る。ミープルを置く／置かないなど、同じタイル配置を共有する候補はタイル配置後の解析結果を再利用する。
4. 元の候補ID・人間の評価を残したまま、結果が同一の候補を学習時の評価単位にまとめる。盤面全体の状態と得点・ミープルへの効果で同一性を確認し、見た目やタイル名だけでは統合しない。
5. 数値特徴量とラベル、同一候補への対応表、検証用メタデータを、元記録とは別の**事前計算JSON**に保存する。人間の自由記述や盤面全体の重複保存は原則含めない。
6. 学習は事前計算JSONの数値だけで候補を採点する。CMA-ESなどで重みを何度変えても、位置別探索・盤面シミュレーションは実行しない。最後に有望な重みだけを、未使用の局面と少数の通常盤面自己対戦で検証する。

事前計算画面には、入力件数、処理済み手番、位置・候補数、経過時間、推定残り時間、現在の段階、停止を表示する。ブラウザの応答を保つためWorkerで処理し、手番または一定作業量ごとに進捗を返す。中断した結果は完成済みJSONとして誤用させない。画面構成や具体的なボタン配置は実装段階で決める。

## 位置別情報

対象位置は、未完成の都市・道の開放辺、未完成の修道院の周辺、未完成の頂点型、便乗・略奪・妨害に関係する近傍に限定する。盤面の無関係な外周全体は走査しない。THIN/FAT、形状、幾何学的位置・向きは混同しない。座標は浮動小数点の表示値ではなく、ゲームの配置照合に用いる安定したキーで記録する。

各位置には、関係する地形IDと所有者・ミープル数、開放辺、隣接辺の地形、頂点の制約、残り山札の種類別枚数、配置できる**物理タイル枚数**を保存する。同じタイル種類が複数の回転・反転パターンで置けても、その位置の残存枚数には1枚として数える。パターンの数は別値とする。置いた場合の即時得点、完成得点、自分と相手の得点差、ミープル返却、残る未完成辺、頂点完成などを、可能なタイル種類・パターンごとに数値化する。地形ごとには、複数位置の対応可能タイル種類の和集合・重複も保持し、THIN/FATの要求が偏るか、異なる引きに対応できるかを求める。

合法性は現在の `GameEngine` が実際の候補に使う規則と一致させる。地形、辺記号の通常／180度パターン、地形の回転・反転、頂点型、重なり、絶対禁則、確定配置との競合、設定で有効なオプションを含む。近似探索から得た枚数は `approximate` と明示し、厳密な合法枚数へ混ぜない。現在の配置可能枚数が0でも、絶対禁則や将来の周辺配置によって変化し得るなら「永久に埋まらない」とは判定しない。残存山札のどのタイルも、変化しない形状・隣接辺・頂点の制約を満たせず、地形の延伸経路も存在しない場合に限り、完成不能を証明済みとして記録する。証明できなければ `unknown` とする。完成不能でも終局時の未完成得点は評価に残す。

完成見込みは、必要な位置ごとの残存タイル候補だけでなく、引くまでの自分の残り手数、引き直し、複数位置でのタイルの取り合いを考慮する。独立でない位置ごとの確率を単純に掛け合わせない。初版で正確な確率を計算できないものは、合法枚数・必要枚数・種類の多様性から得る**近似指標**として保存し、確率という名前を付けない。地形の完成を確実に不可能と証明できた場合のみ、完成確率を0と確定する。

## 候補ごとの数値特徴量

候補は「タイル配置＋ミープル選択」の単位で保存する。少なくとも以下を、評価前後の差分または候補後の状態として数値化する。プレイヤー視点の符号、自分・相手それぞれの値、単位と丸め方を特徴量辞書に固定する。

| 群 | 主な数値 |
| --- | --- |
| 即時得点 | 両者の確定得点、得点差、返却ミープル数、頂点完成数 |
| 地形の将来価値 | 都市・道・修道院・草原ごとの現在／完成／終局見込み得点、所有ミープル数、開放辺、残り必要位置数、合法残存枚数、完成見込み指標、完成不能の証明状態 |
| 位置と山札 | THIN/FAT、初期位置からの距離、確定配置内外、未確定領域に面する開放辺、各必要位置の対応枚数、残存種類の多様性、残り手数 |
| 妨害 | 相手所有地形の完成見込みの前後差、必要枚数・制約の増減、成功時に防げる相手得点、自分の便乗・略奪余地を減らす損失 |
| 便乗 | 合流後の同数所有が成立する見込み、共有できる都市・草原の得点、必要な自手番とタイル、ルート実現可能性、成功時の得点差改善 |
| 略奪 | 合流後の多数所有が成立する見込み、相手から奪える得点、追加ミープル・タイルの費用、ルート実現可能性、成功時の得点差改善。便乗とは独立の群にする |
| 資源と局面 | 残ミープル数、とくに1→0の消費、得点差、残り手数、頂点王の競り合い、序盤の修道院／都市・初期草原、劣勢時の逆転余地 |

得点は完成済みの即時得点と将来の見込みを二重計上しない。地形の所有は多数決と同数取得を区別する。都市・道・修道院の完成得点と未完成終局得点は現行の `Scoring` を正とし、草原は現行の草原ルール設定に従う。道での便乗・略奪を一律に禁止せず、得点の大きさと実現性で低く評価できる構造にする。「都市20点／草原30点」「初手約10手」「頂点差約12個」は初期の目安であり、合法条件や確定ラベルにはしない。

### 高価な戦術探索

1～2枚の便乗・略奪ルート、お互いが望ましいタイルを引いた場合の応手、妨害後の完成経路は、対象地形・位置・残存タイルに限って事前計算する。探索開始条件は、たとえば所有された高得点地形との近接、合流可能な開放辺、相手の高確度な完成など、**重み・教師ラベルに依存しない**固定の条件とする。学習中の重みによって対象候補を変えると、事前計算JSONと実対局の評価が食い違うためである。

枝数・深さ・時間に上限を設け、未探索、探索済みで経路なし、経路ありを区別する。1枚ルートと2枚ルートも区別する。複数の位置で同じ残存タイルを必要とする経路を、独立した成功確率として掛けない。相手の妨害応手も探索範囲・上限とともに記録する。上限で打ち切った場合は0点や不可能とはみなさず `unknown` とする。局面・地形・配置結果の共有部分はキャッシュし、次のミープル選択肢や対称候補で再利用する。

## 同一候補の統合

元記録の全候補・全評価・採用IDは消さない。学習用には、配置後の幾何と地形接続、得点、所有、ミープルの消費・返却、将来の合法手に影響する状態が同じ候補だけを同一クラスとして一度採点する。回転・反転の指定が同じでも結果が異なれば統合せず、指定が異なっても結果が同じなら統合できる。判定に自信がない場合は統合しない。クラスには元の候補IDの配列を残す。

同じクラス内で人間が異なる評価を付けた場合は、黙って一つの教師ラベルにしない。矛盾として検査結果に出し、比較損失から除くか、評価の訂正を促す。未検討候補は負例にしない。重複クラスの数だけ教師信号が増えないよう、手番ごとに損失を正規化する。

## 保存形式と再現性

出力は例として `penrosanne-features-日時.json` とし、形式識別子とスキーマ版を付ける。入力記録のハッシュ、タイル定義・ルール・得点処理・特徴量抽出器の版またはハッシュ、山札構成、設定、生成日時、完了フラグ、局面数、候補数、重複統合数、近似・打切り件数を含める。対象版が異なるJSONを、警告なしに学習へ使わない。新しい特徴量の追加や判定変更があれば、元の判断記録から事前計算し直す。元のJSONも保管し、事前計算JSONだけで人間の判断記録を完全復元できるとは扱わない。

位置別情報と候補特徴量は、数値配列と版付き特徴量辞書で保存し、各候補に長いキー名や盤面を繰り返さない。欠損は `null` または状態フラグで表し、0と混同しない。学習時に使う情報は、手番で公開されていた山札の種類別残数までとし、以後の山札順、終局結果、人間の評価タグを特徴量へ混ぜない。教師ラベルと特徴量は別領域に保存する。選択手と評価の対応はIDで検証する。

## 学習と高速化

学習の評価関数は、事前計算済みの候補ベクトルと重みの積、および必要な軽量な数式だけで完結させる。序盤・中盤・終盤の重みを扱い、起点は現行CPUの重みとする。相関を持つ連続値の調整にはCMA-ESを第一候補とし、初版は特徴量群ごとの比較的少数の重みから始める。入力データが少ない間は、起点重みからの逸脱を抑える正則化を加え、特徴量ごとの独立重みを一度に大量追加しない。重みや正規化の方式、乱数シード、探索予算、採用世代を保存する。

教師損失は、採用候補が「次点」「危険」「悪い」と明示された別候補より上に来ることを基本とし、評価間の強さは別の係数で調整できるようにする。「自信あり」「迷った」「強いか不明」は採用手の確信度であり、ゲーム上の強さを直接示す正解確率ではない。未検討候補は誤りとして扱わないが、全合法候補に対する採用手の順位も**参考指標**として表示する。対局ごとの手数や評価済み候補数によって1局が過大に重くならないよう、手番・対局単位で集計する。

初期の個体比較には局面を層化抽出した小標本を使い、残った個体だけ全学習局面で採点する。標本は序盤・中盤・終盤、採用手の確信度、評価済み代案、戦術タグの有無を偏らせず、世代ごとに入れ替える。上位候補を落とす可能性があるため、この段階評価だけで最終採用を決めない。小標本の採点は同一世代の個体間で共通の局面・乱数シードを使う。個体の採点は独立なのでWorkerで並列化できるが、まず単一Workerで計測し、端末のメモリ量に応じて数を抑える。

自己対戦は毎世代・全個体には行わない。教師データと未使用の記録局面で改善した少数の候補のみ、最後に未使用シードと通常の確定配置探索を使う先後交換の対戦で確認する。2人戦の勝率を主指標、同率なら得点差を使う。固定盤面を用いる対戦は性能測定や予備選抜には使えるが、最終評価を置き換えない。自己対戦の結果が悪い候補を自動的に本体CPUへ反映しない。

## 実対局との一致と検証

### ブラウザでの実行

`npm run serve` で起動し、ゲーム画面の「開発用」→「Feature Training」から専用画面 `feature-training.html` を開く。既存の `cpu-training.html` とは独立した画面である。判断記録JSONを読み込んで特徴量を生成し、特徴量JSONとして書き出す。生成には長時間かかるためWeb Workerで処理し、手番ごとに進捗を表示する。以前書き出した特徴量JSONを読み込めば生成を省略できる。

特徴量を使ってCMA-ESで重みを学習し、CPU JSONを書き出す。最後に書き出したCPU JSONを2つ指定すると、通常の確定配置探索を使う標準2人戦を、同じ山札シードで先後交換して比較できる。1～5組の少数対戦とし、結果もJSONに書き出せる。停止ボタンは現在のWorkerを終了する。ブラウザで生成したJSONは自動保存せず、次回利用時はファイルから読み込む。検証結果が良くても本体CPUには自動反映しない。


通常対戦CPUも同じ特徴量定義・数値化関数を使う。ただし実対局では新しい盤面から必要な局所情報を計算し、可能な範囲で前手番の結果を増分更新する。事前計算JSONを対局中に読み込む方式にはしない。事前計算時と実対局時に同一の盤面・候補を与えたら同じベクトルになる回帰テストを用意する。

- 記録JSONから選んだ手番で、位置別の合法枚数がエンジンの候補と一致すること。特に回転・反転、THIN/FAT、確定配置との競合を検証する。
- 完成不能の証明で、将来埋められる位置を誤って0としないこと。`unknown` と0の区別を検証する。
- 対称候補を統合しても、各元候補ID、人間の評価、採用手への対応が失われないこと。異なる結果は統合しないこと。
- 同じ事前計算JSON・重み・シードから同じ順位と学習結果が得られること。重み変更のたびに `Board`、`Rules`、`Scoring`、戦術探索を呼ばないこと。
- 事前計算の所要時間・ファイルサイズ、学習1個体・1世代の時間、Workerのメモリ使用量を別々に計測する。旧方式との速度比較は同じ記録・同じ端末で行い、教師指標も比較する。
- 検証用の対局・シードは学習と事前選抜に使わない。盤面を直接編集した局面は検証用にも使わない。現在の少数の記録だけでは真の勝率向上を保証しない。
