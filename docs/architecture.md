# Penrosanne アーキテクチャ仕様（草案）

## 1. 方針

ゲームのルール、CPU、通信、描画を分離する。特にゲームルールはブラウザやネットワークに依存しないため、ローカル対戦・CPU戦・オンライン対戦で同じ `game` モジュールを再利用できる。

### 盤面描画の負荷対策

- ブラウザでは確定配置の探索を開始する前に「盤面を拡張中…」と待機カーソルを描画する。24枚追加または約60msの処理区間ごとに描画機会を設け、追加枚数を更新する。追加がない頂点検査中も区切る。開発用の順次表示がオフでも探索を分割し、結果の枠のみ最後にまとめて表示する。同期探索APIは従来通り残す。
- パン・ホイール・ピンチのカメラ座標は入力ごとに更新し、再描画要求だけを `requestAnimationFrame` でまとめる。配置アニメーション等の直接描画は予約済み描画を取り消し、二重描画を防ぐ。
- 画面外の配置済みタイル・配置候補・確定枠は描かない。判定にはタイル全頂点を含む半径と、画面上24pxの余白を使い、側面や影を画面端で切らない。履歴のタイル番号は元の配列の番号を維持する。
- 角丸輪郭は `Path2D` を再利用する。ローカル輪郭は形状と寸法で最大32件、盤面上の輪郭はタイルをキーとする `WeakMap` で保持し、形状・寸法・位置・回転が変われば再生成する。テーマ画像のクリップにも同じローカル輪郭を使う。
- 側面、上面、ホバー、ミープルの重ね順と、画面上の厚みは従来通り。ビットマップへの置換や解像度の低下は行わない。
- `scripts/benchmark-board.html` は500枚の合成盤面で、従来の側面パス再生成・画面外描画との比較と画素差を表示する開発用ページ。表示する時間はCanvas描画命令の実行時間であり、ゲーム全体のFPSやGPU描画完了時間ではない。

## 3. モジュール責務

| モジュール | 責務 |
| --- | --- |
| `GameState` | 不変または安全に複製可能なゲーム全状態 |
| `GameEngine` | 手番進行、操作受付、状態遷移、イベント発行 |
| `Tile` | タイル種別、辺ごとの地形、内部の特徴領域、辺記号パターン、回転後の情報 |
| `TileSet` | タイル定義から山札を生成する |
| `Board` | 直交座標の配置済みタイル、辺記号・地形の接続、隣接検索、連結領域検索。辺一覧を盤面更新までキャッシュする |
| `TileTheme` | テーマ別の透過PNGを遅延読み込みし、タイルの地形レイヤーを回転・ミラーに追随して描画する。欠損画像はCanvas描画へフォールバックする |
| `Player` | プレイヤー情報、得点、残コマ、種別（人間／CPU） |
| `Rules` | 合法手、コマ配置可否、完成判定 |
| `Scoring` | 完成・終局時の得点計算 |
| `CpuPlayer` | 状態を評価してゲーム操作を選ぶ |
| `Host` | 対戦ルームとゲーム状態の管理、操作検証・配信 |
| `Client` | ホスト接続、操作送信、状態同期 |
| `Protocol` | ネットワークのメッセージ種別とペイロード定義 |
| `BoardView` | Canvas/SVGによる盤面描画、配置候補表示、マウス／タッチのスナップ操作 |
| `TileDrag` | 把持点を保持するドラッグ、持ち上げ・着地アニメーション、合法候補の着地点表示。ゲーム状態は変更せず、仮置きをUIへ返す |
| `ui/i18n` | 日本語を既定とする表示文言の辞書、言語切替、ブラウザ内での選択言語の保持 |
| `PlayerPanel` | 手番・得点・コマ数の表示 |
| `GameUI` | 画面遷移、操作入力、各UI部品の統合 |
| `GameSetupUI` | モード・ルール・テーマなど、開始前設定の入力と検証 |

## 4. 依存方向

```text
ui ────────┐
ai ────────┼──> game
network ───┘
main ─────────> ui / game / network
```

- `game` は `ui`、`ai`、`network` を import しない。
- `ui` と `network` は `GameEngine` の公開APIだけを使う。
- CPUも人間と同じゲーム操作（タイル配置、コマ配置、手番終了）を使う。

### 空白防止判定のキャッシュ

このキャッシュは、ルール上の「禁則配置」判定を高速化する実装であり、デッドエンドの完全な検出を保証するものではない。

- 各空き辺について、シンまたはファットが重ならずに入る物理的証人の有無をキャッシュする。
- タイル配置後は、新タイルの辺と中心から辺長の約3倍以内にある空き辺だけを再検査する。
- 手番タイルの候補は、地形・重なり・辺記号・頂点型を満たす配置を基準に、空白防止キャッシュで絶対禁則を除外した通常候補だけを返す。
- 近傍辺でも、既存の候補がまだ合法なら再探索しない。離れた空き辺は前回の結果を利用する。
- キャッシュ有無で候補集合が一致することをテストで保証する。

### 形状確定配置の増分探索

- `Rules.structuralPlacementFrontier` は、地形を持たないシン／ファットの仮想タイルで、ルール3の頂点型だけから確定配置を探索する。頂点記号を単純連結せず、各タイルが占める扇形と頂点型スロットを照合するため、未配置の扇形をまたぐ合法候補を除外しない。辺記号・地形・空白防止はこの探索に含めない。
- 頂点をキュー単位として、`C`、2枚、3枚、4枚以上の指定列の優先順に完成形を局所列挙する。完成形が複数ある場合も、すべてに共通する位置だけを確定するため、`BDGG`／`GGBD` のように型は曖昧でも共通部分を連鎖できる。
- 仮想盤面には確定配置を保持し、次の実盤面探索へ引き継ぐ。確定位置への実配置は再探索しない。非確定位置への実配置だけを仮想盤面へ追加し、新タイルの4頂点から探索を再開する。仮想盤面は `GameState` に保存しない。
- `BoardView` は確定配置を薄い灰色の実線で表示する。未確定配置は記録・描画しない。手元タイルは既存どおりの候補表示を使い、確定配置と異なる位置で重なるものだけを除外する。

## 5. 状態遷移

「私的な都市計画」は `GameState.handMode` とプレイヤーID別の `hands`、`consecutivePasses` を保持する。`currentTile` は選択中の手札、またはミープル配置中の実配置タイルを参照する。UIからの手札選択・引き直し・パス・配置は `GameEngine` の操作で検証する。手番終了時に配置したプレイヤーへ補充し、山札切れ後も手札が残る限り続行する。

同モードの確定配置探索は3枚で共用し、地形を含む合法候補を手札別にキャッシュする。候補には元の手札IDを付け、UIの配置場所表示だけを統合する。実配置で手札別キャッシュを無効化し、引き直しでは交換した手札の分だけ更新する。公開手札とタイル選択の吹き出しは `PublicHands` と `main` が描画し、回転・反転・ドラッグの候補は選択した手札IDに絞る。

`DRAW_TILE` → `PLACE_TILE` → `PLACE_MEEPLE` → `SCORE_COMPLETED` → `NEXT_TURN`

UIは現在フェーズに応じた操作だけを提示する。オンラインではホストが各フェーズの妥当性を検証する。

## 6. 状態の保存と再現性

- `GameState.turnHistory` は手番ごとに配置タイルID、盤面枚数、プレイヤー、配置したミープル、採点直前／回収後のミープル一覧、完成得点を保存する。履歴のホバーは採点直前の状態を表示し、後から置かれた現在のタイル・ミープルを薄く描く。確定配置・候補は現在のものを維持する。
- 終局時は開始タイルから履歴を高速再生してから得点を表示する。リプレイは表示専用でルールや探索を再実行しない。最終盤面の外接範囲に画角を合わせ、再生中の盤面操作を停止する。終了後はその画角から操作を再開できる。

- `GameState` はJSONにシリアライズ可能なデータだけで構成する。
- `GameConfig` は対局開始時に確定し、開始後は不変として扱う。テーマなど表示専用の設定も同期・保存対象に含める。
- 乱数にはシードを持たせ、同じシードと操作履歴から同じ対局を再現できるようにする。
- オンライン同期では、原則としてホストが送る確定状態または操作イベントを使用する。
