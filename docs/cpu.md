# CPU・ローカル自己対戦仕様

## 目的と範囲

通常対局では、CPUは人間と同じ `GameEngine` の公開操作だけを使い、合法判定・採点にCPU専用の例外を設けない。強化の主指標は**2人戦の勝率**、同率の比較指標は**最終得点差**とする。最初の対象は基本ルール「スタンダード」（`standard` 山札、1枚手札、草原あり、頂点王のみ有効、設置規則はすべて有効）。山札の枚数や内訳は `TileSet.js` の現在の定義に従い、CPU用に複製・固定しない。

画面なしのローカル対戦に加え、設定画面の各プレイヤーのCPUスイッチをブラウザ対局へ接続する。新規対局時に選択を反映し、対局中の設定画面から切り替えた場合も閉じた後の手番に反映する。CPU手番中は人間による配置・引き直し操作を受け付けない。設定画面を開いた場合はCPUの仮置き・待機を中断し、閉じた後に現在のフェーズから再開する。CPUも既存の候補探索・タイル配置・ミープル配置・得点処理を使い、独自の合法判定は設けない。演出・Canvas・待機タイマーは画面なしの自己対戦には持ち込まない。

ブラウザでは2〜4人戦と公開手札3枚にも対応する。CPUは公開されている全手札の合法候補から1枚を選び、3枚とも置けなければ山札がある間は無料の引き直し、山札が空ならパスを行う。2人・1枚手札では第2段階の妨害・便乗の局所先読みを使用する。3〜4人戦や3枚手札では処理量を抑えるため一次評価で選び、相手の代表を現在の最高得点者とする暫定評価である。設定のCPUスイッチはすべて操作主体を切り替えるもので、対戦難易度の個別設定はまだない。

## 情報と行動

- CPUが使ってよい情報は公開済み盤面、自分の手札・残ミープル、得点、公開された山札構成と使用済みタイルから推定できる残り枚数まで。山札の**次の順番を見て評価してはならない**。再現用に対戦実行器が順番を保持することとは分ける。
- 行動は合法候補から選ぶタイルの位置・向き、ミープルの合法領域または「置かない」を一組として評価する。実際の確定時にも `GameEngine.placeTile` と `placeMeeple`／`skipMeeple` を通す。
- 初版は任意の引き直し権を使わない。候補がないタイルの自動破棄・引き直しは既存エンジンに従う。引き直し判断は後の行動空間拡張とする。
- 同点の手は、山札とは独立したシード付き乱数で決める。同じ盤面・設定・シード・CPU重みから同じ判断が得られるようにする。

## 盤面評価

現行の第0世代は、2026-09-26に採用された重み（`immediate 0.636`, `future 1.217`, `meepleCost 1.100`, `fieldMeepleCost 1.483`, `fieldFuture 0.220`, `vertex 0.571`, `obstruction 0.280`, `poach 0.826`, `poachProximity 0.047`, `obstructionMobility 0.550`, `poachBridge 1.027`）を基準とする。序盤・中盤・終盤の初期値はこの同じ値で揃え、世代を進めながら独立に変異させる。局面の進行率は配置済み・山札・破棄済み・手札・現在タイルの合計に対する配置済み数で求め、3分割した区間を使う。

初版は候補全体を軽い局所指標で並べ、上位候補だけに仮盤面上の重い評価を行う。仮盤面は本物の対局状態を変更せず、既存の `Board`・`Rules`・`Scoring` を利用する。評価値は最終得点ではなく比較用の暫定値であり、重みは対局ロジックから分離する。

評価項目は、自分と相手の即時得点差、未完成都市・道・修道院の見込み、草原の見込み、ミープルを手元に残す価値、頂点王への進捗、妨害、便乗である。未完成地形の見込みには規模と開いた辺の数を使い、完成済みの得点と二重計上しない。初版の妨害は、相手所有地形の開いた辺を増やす・完成見込みを下げる局所指標とする。初版の便乗は、別々に所有された同種地形の距離と、連結時のミープル多数決による見込みを使う**幾何学的な弱い予兆**に留める。距離が近いだけで合法な連結経路があるとは断定しない。

第2段階では、公開済みの山札構成から盤面・破棄済み・現在の手札を差し引いた、種類別の残存枚数を使う。一次評価の上位3行動だけ、相手地形の開放辺に次の1枚を置ける残存タイル枚数を調べ、配置前後で完成しやすさが下がる手を妨害として加点する。便乗は、自分と相手の別々の都市・道に対し、残存タイル1枚で両方へ辺・地形・頂点の規則に合う接続を作れる場合だけ追加で加点する。単なる近接だけでは、この追加加点をしない。探索は近い開放辺の組に制限する。仮想の次手は絶対禁則と確定配置との競合まで再探索しないため、厳密な「次手の実配置確率」ではなく局所的な実現可能性の近似である。実際に選ぶ現在の手は従来どおり `GameEngine` の完全な合法候補に限る。

さらに先の段階では、絶対禁則と確定配置まで含む残存タイル種類の検証、便乗の2枚橋渡し、得点共有・横取りの成立確率を加える。これらは高価なので、全候補ではなく一次選抜した手だけに適用する。未来の山札順は使わない。

## ローカル自己対戦と強化

### ブラウザ内の世代訓練

`npm run serve` でローカルサーバーを起動し、`http://127.0.0.1:4173/` の開発用設定にある「CPU訓練画面を開く」、または `http://127.0.0.1:4173/cpu-training.html` から、盤面を描画しないローカル自己対戦を実行できる。モジュールWorkerと固定盤面JSONの読込が必要なため、訓練画面を `file://` で直接開く方式は対象外とする。Web Worker で訓練を進めるため、画面には世代・対局・手数の進捗だけを表示する。ブラウザ上の訓練では現在のスタンダード山札と訓練専用の固定確定配置3パターンを使う。実際のゲーム本体の合法判定や山札定義は変更しない。

個体数・1世代の対戦数・進める世代数・重みの変異の強さを指定する。個体は現行基準1体とその重みを変異させた挑戦個体で構成する。公平な比較のため、各挑戦個体は基準と同じシードで先後を交換して戦う。したがって1世代の対戦数は `2 × (個体数 - 1)` の倍数とする。勝率を優先し、同率なら基準に対する得点差で最優秀個体を選び、その重みを次世代の基準にする。初版は比較相手が現行基準であり、個体同士の総当たりではない。少数対局の結果は揺れやすいため、正式な強さの評価には別シードと通常盤面での検証を要する。

各世代の全個体の重み、勝分負、得点差、採用個体、対局ごとの操作ログをブラウザ内の IndexedDB に一時保存する。保存できるのは保存順で直近10世代だけで、11件目以降は古い記録を削除する。長期保管や別ブラウザへの移動にはJSONを書き出す。保存済みの世代を選ぶと各重みと採用個体の前世代からの差を確認できる。重みの列は `DEFAULT_CPU_WEIGHTS` の項目から動的に作るため、評価項目を追加しても既存記録の欠けた項目はその時点のデフォルト値で補われる。

自己対戦・教師あり学習の開始には、世代JSONを1ファイル読み込む。`cpu-generation-data` のドロップダウンから選ぶ方法と、端末上のJSONを直接指定する方法がある。そのファイル内の最大世代番号の採用重みだけを起点にし、ブラウザの一時保存の最新世代は起点にしない。教師あり学習の手動対局ログも `battle-data` のドロップダウンまたは直接ファイル指定から読み込め、フォルダーの1件と直接指定した複数件を併用できる。開始前に系統名を入力し、新しい世代は「系統名＋起点の世代番号から加算した番号」で表示する。異なる系統で同じ世代番号が生じても別記録として扱う。訓練画面の世代間総当たりでは、2～4ファイルそれぞれの最新世代を読み込み、各組み合わせで先後を交換して2対局ずつ行い、勝分負・合計得点・得点差を表示する。対戦結果は世代データとして保存しない。

ゲーム本体では設定画面の開発用項目から `cpu-generation-data` 内の世代JSONを選び、さらにそのファイル内の世代を選べる。既定は更新日時が最新のファイル内の最大世代番号の採用重みで、フォルダーが空または利用できなければ初期重みを使う。ブラウザの直近10世代キャッシュからは通常対戦用CPUを選ばない。選択した重みは全CPUプレイヤーの手の評価だけに渡し、合法配置・得点ルールには影響しない。フォルダーの一覧取得には `npm run serve` のローカルサーバーを使用する。

- Node.jsの単独コマンドでCPU同士を繰り返し対戦させる。実行中にCodexや外部APIを呼ばない。
- 山札用とCPUの同点選択用に独立した乱数系列を使う。比較では同じ山札シードで先後を交換した**2対局を1組**にする。
- 初版は逐次実行とし、1・10・100組の所要時間とメモリを測ってから並列ワーカー数を決める。画面処理を除いても確定配置・合法候補の探索負荷は残る。
- 重みの改良は、変更案と保存済みの基準CPUを複数のシードで比較する。主指標は勝率、同率時は得点差。調整に使っていないシードでも再評価し、成績の悪化した重みを自動採用しない。同一重み同士の自己対戦だけでは強化を判定できない。
- 通常ログには選択した操作だけを保存し、全候補の一覧や仮盤面を毎手保存しない。対局ごとの結果、シード、CPU重み、山札・コードの版、配置の座標・向き、ミープル配置、得点を後から確認できるようにする。完全な再現には当時のタイル定義とコード版を保持する。
- ブラウザ内自己対戦では各手の段階、選択時評価値、候補数、得点推移を保存する。勝敗・最終得点差が同じ個体は、序盤・中盤・終盤の得点差推移を次の比較基準にする。
- 妨害・便乗の改善には、自己対戦の成績に加え、戦術が成立する固定盤面の回帰テストを用いる。最終的な選択は必ず通常の合法判定を通し、違法手はテスト失敗とする。

初版のコマンドは `npm run self-play -- --pairs 5 --seed 1 --out <新しい出力フォルダー>`。1組は先後を交換した2対局で、`run.json`、`summary.jsonl`、`result.json`、各対局の `game-*.json` と読み返し用の `game-*.txt` を保存する。候補を全件記録せず、各手にはタイルID・形状・中心座標・回転・マッチングと地形パターン・ミラー状態・ミープル・評価値・完成得点イベントを記録する。山札とCPUのシードを分離し、初期山札のハッシュと関連コードのハッシュを残す。同じ重み同士の実行結果は動作確認用であり、勝率の強化判定に用いない。

重みの自動試行は `npm run train-cpu -- --rounds 3 --pairs 2 --validation-pairs 1 --seed 1 --out <新しい出力フォルダー>`。毎回2項目の重みを小幅変更し、現行の `best-weights.json` に対して先後交換で比較する。勝率を優先し、勝敗数が同じときだけ得点差で判定する。改善が見られた候補は異なるシードでも検証してから採用する。対戦は逐次実行であり、画面処理もCodex APIも使わない。長時間の実行はローカルPCのCPU・メモリを消費する。再開するときは前回の `best-weights.json` を `--weights` に指定して新しい出力フォルダーを作る。

重みは仮値であり、自己対戦の成績は実力の保証ではない。第2段階の実測1対局（seed 7、83手）は約197秒で、CPUの思考が約4.5秒、主にエンジンの合法候補・確定配置探索が約193秒だった。対局ごとに盤面が異なるので、旧版との単純な秒数差を性能改善とみなさない。表示を省くだけでは1対局が瞬時には終わらない。並列化は計測後に判断する。

### 固定確定配置による高速な訓練対局

訓練専用のオプション `--patterns <フォルダー>` を `self-play` / `train-cpu` に渡すと、保存済みの確定配置の位置集合を使用する。通常のブラウザ対局とオプションなしの自己対戦は従来どおり盤面ごとに確定配置を探索する。固定モードでは初期タイルと同じ形状の保存済み位置から盤面中央に最も近いものを選び、固定盤面全体を回転・平行移動して初期タイルを原点・回転0に合わせる。以後、固定盤面に含まれないタイル位置は候補から除外し、確定配置の増分探索を一切実行しない。地形、辺記号、頂点型、重なり、絶対禁則、得点、ミープルの通常判定は変更しない。

固定盤面は位置と形状・回転のみを保存し、地形や山札順は固定しない。標準山札の定義は変更しない。抽出用の長時間対局だけ、現行の標準山札を追加で複製して使い、確定配置がおよそ1200枚（最低1100枚）に達した瞬間の実タイルと確定位置を保存する。保存済み3例は `training-patterns/standard-training-v1` にある。新たな例は `node scripts/generate-training-patterns.mjs --count 3 --out <新しいフォルダー>` で抽出できるが、条件に達しない試行は飛ばすため時間がかかる。固定モードでは配置可能範囲が異なるため、訓練の高速化に用いても、最終的な実力評価は固定盤面を使わない通常対局と未使用のシードでも確認する。

使用例は `npm run train-cpu -- --rounds 3 --pairs 2 --validation-pairs 1 --seed 1 --patterns training-patterns/standard-training-v1 --out <新しい出力フォルダー>`。先後を交換する2対局には同じ固定パターンを使用し、シードを変えると3例を順に使用する。`--patterns` を省けば通常対局へ戻る。

計測例：`npm run benchmark:training-pattern -- --pattern training-patterns/standard-training-v1/pattern-01.json --seed 7`。同一PCで続けて実行した1対局ずつの結果は、固定盤面が82手・46.0秒、通常盤面が83手・238.7秒で、対局全体で5.19倍、1手当たりで5.13倍だった。固定盤面は手の選択や破棄枚数も変わるため、これは**訓練対局の所要時間**の比較であって、同一局面の確定配置探索だけを測るマイクロベンチマークではない。

## 後続段階

1. 第2段階の自己対戦を複数シードで計測し、重みと局所評価を調整する。
2. 妨害の完成必要枚数と絶対禁則、便乗の2枚橋渡し探索を追加する。
3. 任意の引き直し判断と、3〜4人戦・公開手札3枚の評価精度を改善する。CPU高速化は演出だけを変え、同じ難易度なら判断を変えない。

### 教師あり学習とデータ移行

開発用設定の「手動対局ログを書き出す」は、対局シード、設定、各手の直前の盤面・手番・山札残数・引いたタイル・配置候補一覧、実際のタイル向きとミープル選択、得点・引き直し履歴を日付時刻入りJSONとして保存する。候補一覧と盤面状態を各手に含むため、ログのファイルサイズは通常のプレイログより大きい。CPU訓練画面の教師あり学習はこのJSONを読み込み、実際に選ばれた手がCPU評価の上位1・3・5候補へ入る回数と平均順位を序盤・中盤・終盤ごとに集計する。各世代の全個体を三段階すべての局面で評価し、次世代は段階別の優秀個体から作った重みをそれぞれ引き継ぐ。

教師あり評価の最優秀基準は、上位5候補に含まれる割合、上位3候補に含まれる割合、1位一致率、平均逆順位の順である。これは人間の選択を再現する指標であり、勝率やゲーム上の強さを直接保証するものではない。教師あり世代もJSONに書き出して `cpu-generation-data` に置けば、対局本体でCPU世代として選択できる。

CPU訓練画面のJSON書き出しには、ブラウザに一時保存中の直近10世代だけが含まれる。ブラウザ内に世代がない場合は第0世代の基準JSONを書き出せる。JSON読み込みでも一時保存の上限10世代を維持する。「一時保存をリセット」は確認後にブラウザ内の世代キャッシュだけを全件削除し、書き出し済みJSONファイルや画面に読み込んだ学習起点ファイルは変更しない。ブラウザを変えるときは旧ブラウザで書き出し、新ブラウザで読み込む。新しいCPU重み項目を追加した場合、古い記録にその値がなければ現行デフォルトを使い、記録に未知の数値項目があれば世代表示・変異用データに保持する。
